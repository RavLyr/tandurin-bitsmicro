# F-03: Crop Recommendation

| Field | Value |
|-------|-------|
| ID | F-03 |
| Name | Crop Recommendation (micro-condition analysis) |
| Priority (MoSCoW) | Must |
| Depends on | F-02 |
| Status | Draft |

## 1. Business Description

F-03 is the core consultative value of Tanduri. After the user describes their planting context in natural language, the Agronomist Agent extracts micro-condition entities (land area, geographic location, growing media, water availability, sunlight, budget, skill level), augments them with real weather data and fresh reference search, and returns 2–3 optimal crop recommendations. Each recommendation carries a compatibility rating, agronomic reasons, an estimated planting window, expected harvest time, and care notes.

The feature turns vague intent ("saya ingin mulai tanam sayur di balkon") into a concrete, defensible planting plan that F-05 (Task Generator) can later turn into a daily schedule. It works within the SMS-style chat from F-01/F-02, output in Indonesian Markdown.

## 2. User Stories

- As a beginner gardener, I want to describe my land (area, location, sunlight, water, budget) and receive crops that fit my conditions, so I stop killing plants.
- As a user, I want weather that fits my exact location, so my planting window matches the real season.
- As a user, I want fresh, source-backed advice, so recommendations do not rely on outdated generic lists.
- As a user, I want to confirm the plan, so I can later receive a care schedule generated by F-05.

## 3. Acceptance Criteria

1. Given a chat message with at least location/land details, F the Agronomist emits the `land_conditions` JSON before any tool call.
2. When location (lat/lon or place name) is present, the Weather Tool is called once per (lat, lon); results used in the recommendation.
3. When the user asks for current-season or market-relevant crops, the Search Tool is invoked; sources are appended after the crops shown.
4. F the response lists ≥2 crops, each with: crop name, compatibility rating, reasons, planting window, expected harvest, care notes.
5. All F render as valid Markdown in Indonesian, embedded in `messages.content` (assistant).
6. After each recommendation the agent asks: "Apakah rencana ini sesuai? Saya bisa buatkan jadwal perawatannya."
7. When the user answers "sesuai/ya", a `plan_confirmed` metadata record is created, used as F-05 trigger.
8. The recommendation is never discarded: category/search-hist link F saved in chat history even if not confirmed.

## 4. Data Requirements

- `messages` table: `content` stores the full Markdown recommendation (assistant message).
- `messages.metadata` (jsonb, nullable):
  - Recommendation: `{ "type": "recommendation", "crops": [...] }`
  - Confirmation: `{ "type": "plan_confirmed" }`
- `weather_cache` table (Supabase): `lat numeric, lon numeric, payload jsonb, fetched_at timestamptz, PRIMARY KEY (lat, lon)`.
- `land_conditions` JSON schema (intermediate, in-conversation):

```json
{
  "area_m2": 12,
  "location": "Semarang",
  "latitude": -6.9667,
  "longitude": 110.4167,
  "media": "soil",
  "water": "plenty",
  "sunlight": "full",
  "budget_idr": 500000,
  "experience": "beginner"
}
```

### Notes

- Writing code to handle every uncovered entity is NOT required (YAGNI). Handle only `location`, `latitude`/`longitude`, and one string `name`; ignore everything else. The spec is intentionally minimal.
- Cache only base string → lat/lon (30 min). Pinning a region is outside scope.

## 5. Data Requirements

- `weather_cache` table:
  - `lat` numeric, `lon` numeric, `payload` jsonb (temp, humidity, rain description), `fetched_at` timestamptz. Primary key: `(lat, lon)`.
  - TTL: 30 minutes. On write, upsert `(lat, lon)` only.
- Search source URLs never stored; deduplicate while recommending.

## 6. Integration

- Orchestrator Agent → Agronomist Agent (sub-agent).
- Gemini function calling (function declarations via `@google/genai`):
  - `weather_lookup` — OpenWeatherMap current weather by lat/lon; free tier 1000 req/day; key `OPENWEATHER_API_KEY`.
  - `search_references` — Gemini `google_search` grounding, no extra key.
- `weather_cache` table: upsert `(lat, lon)`; TTL 30 min.
- Messages flow F-02 → F-03; `plan_confirmed` → F-05.
- Weather API failures tolerated: recommend from LLM knowledge, note "data cuaca tidak tersedia".

## 7. Edge Cases & Error Handling

1. Missing location/lat-lon → ask clarifying question; do **not** call tools.
2. Weather API failure/timeout → proceed with LLM knowledge; add note "data cuaca tidak tersedia".
3. Entity extraction missing entities → agent asks one targeted follow-up (no tool call).
4. Land area invalid as field (e.g. 0 m²) → treat as "unknown area", keep recommendation operable.
5. Unsupported media/water/sunlight values → reject entity, run with defaults, tell user.
6. No search result / no network → fall back to LLM knowledge results.

## 8. Definition of Done

- [ ] Natural-language chat → entity extraction → tool calls → valid recommendations.
- [ ] At least 2 crops recommended, each with all 5 required fields.
- [ ] Confirmation "Apakah rencana ini sesuai?" asked and handled.
- [ ] `messages.metadata` persists `{type:"recommendation"}`/`{type:"plan_confirmed"}` verified in Supabase.
- [ ] Sources listed when search used.
